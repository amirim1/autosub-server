# AutoSub Server — Codex Engineering Guide

## Project Understanding

Перед изменением кода:

1. Проверь `git status` и не затрагивай чужие незакоммиченные изменения.
2. Изучи структуру проекта, `README.md`, релевантные документы в `docs/` и текущую реализацию.
3. Найди существующие точки входа, зависимости и похожие решения.
4. Определи критерии готовности и потенциальные риски.
5. Только после этого вноси минимальное изменение.

AutoSub Server — локальный FastAPI-прокси JSON-подписок 3x-ui. Основные границы системы: HTTP-роуты в `autosub_server.py`, генерация подписок в `builder.py`, интеграция с 3x-ui в `api_client.py`, SQLite в `storage.py`, админ-панель в `dashboard.py` и `templates/`.

Поток подписки обычно проходит так: `/json/{sub_id}` или `/sub/{sub_id}` → `builder.build_for_subscription()` → `api_client` за оригинальной подпиской → `storage` за группами/правилами → JSON-ответ. Legacy `/sub/` выбирает HTML или JSON по типу клиента. Не меняй этот контракт без отдельной проверки клиентов.

## Core Principles

- Делай только запрошенную работу; не добавляй функции «на будущее».
- Сначала переиспользуй существующие утилиты и архитектурные решения.
- Предпочитай минимальный, понятный diff без лишнего рефакторинга.
- Не меняй публичное поведение, формат подписок или схему данных без явного обоснования.
- Не создавай новые файлы и зависимости без необходимости.
- При действительно неоднозначных или рискованных требованиях задай вопрос до изменения.

## Git Safety

- Не делай commit или push без прямого запроса пользователя.
- Не делай force push, не переписывай историю, не удаляй ветки или теги.
- Перед серьёзными изменениями проверь `git status`.
- Уважай рабочую ветку `dev`; релизные действия выполняются только по отдельному запросу.
- Не удаляй и не откатывай пользовательские изменения.

## Change Discipline

- Одна логическая задача за раз.
- Изменяй минимальное число файлов.
- Не меняй архитектуру, API и формат данных, если задача этого не требует.
- Не добавляй зависимость без проверки необходимости, совместимости с Python 3.10+ и обновления документации.
- Секреты и конфигурация берутся из окружения; не храни их в коде, логах или документации.

## Testing and Verification

После изменения запускай релевантные проверки и сообщай точные команды и вывод:

- `python -m pytest -q` — основной набор тестов.
- При изменении конкретного модуля — соответствующие тесты из `tests/`.
- `python -m compileall -q *.py` — базовая проверка синтаксиса Python.
- `ruff check .` и `pyright` — обязательные статические проверки.
- `python -m pytest --cov=. --cov-branch --cov-fail-under=70` — минимальный coverage gate.
- На Linux для shell/deployment-изменений: `bash -n install.sh update.sh setup_nginx.sh finish_setup.sh`.
- На Linux перед Nginx deployment: `nginx -t`; после systemd-изменений: `systemctl daemon-reload` и `systemctl status autosub-server --no-pager`.
- Для dependency/security-проверок используй project gates `pip-audit`, `bandit` и `shellcheck`.
- Для install/update/systemd/nginx-изменений выполняй доступные статические проверки и явно отмечай, что реальный Linux/systemd smoke test не запускался.

Нельзя писать «тесты прошли», если команда фактически не выполнялась. Если проверка невозможна, укажи причину и остаточный риск.

## Code Quality and Security

- Читаемость важнее краткости; избегай сложных абстракций.
- Валидируй внешние входы и сохраняй защиту CSRF, Basic Auth, rate limit и trusted-proxy модели.
- Не ослабляй TLS-проверку, обработку forwarded-заголовков или изоляцию админ-панели без явного запроса.
- Помни, что SQLite и подписочные метаданные содержат чувствительные данные.
- Учитывай обратную совместимость `/json/`, `/sub/`, заголовков подписки и миграций SQLite.
- Сохраняй различие `XUI_SUB_URL` (subscription upstream) и `XUI_API_URL` (панель/API), а также fallback `XUI_URL`.
- Изменения SQLite должны учитывать `meta`, `client_groups`, `node_catalog`, `group_rules`, `autoselects`, `client_group_overrides` и миграцию legacy `config.json`.

## Communication

В финале каждой задачи сообщай:

### Изменения
Файл и что изменено.

### Проверки
Команда и реальный результат.

### Риски
Что осталось потенциально опасным или непроверенным.

### Не выполнено
Что намеренно не делалось и почему.

## Project Memory

Используй `.codex/MEMORY.md` только для устойчивых сведений о проекте, решений, известных проблем и ограничений. Обновляй его после подтверждённых архитектурных решений, изменения команд, deployment-процесса или важных известных проблем. Не записывай временный контекст задачи, персональные данные, токены, пароли, cookies или содержимое секретных конфигураций.
